机械臂两控制器、底盘两控制器均检查为 `running`。导航同时验证了 360 点激光、IMU/里程计坐标系、地图以及 TF 连通性。

开启 EKF 时，`odom → base_footprint` 唯一发布者为 `/ekf_localization`；关闭 EKF 时为 Gazebo 内运行的底盘控制器（ROS caller ID 为 `/gazebo`）。`map → odom` 在导航时只由 `/amcl` 发布，在建图时只由 `/slam_gmapping` 发布。Gazebo 真值只被验证代码读取用于比较，没有作为定位、规划或控制输入。

上表记录初次验收的具体数值；随后通过独立复验脚本再次检查了机械臂、底盘、导航和建图入口，并在修复脚本的启动时钟竞态后重测了底盘、无 EKF 绕障导航和建图。各次运行均通过，仿真时间模式也已确认。

这些数值来自上述工况，复验时会随传感器噪声、仿真实时率和调度变化。短程 SLAM 已完成更新、保存、加载和一次导航；评估精度与稳定性需要重复实验，评估完整地图质量需要绕场探索并检查闭环、遮挡及未知区域。

## 修复并验证的模型问题

早期底盘存在支撑与接触响应问题：轮式里程计与实体运动明显不符，严重时出现约 `0.38 rad` 的俯仰，导致导航目标超时。最终模型采用两驱动轮和单后脚轮，质心后移；轮与脚轮的接触设置为 `kp=1e6`、`kd=500`、`minDepth=0`。修改后通过上表的实体运动和完整导航检查。

这些参数描述 Gazebo 接触弹性和阻尼。移动底盘使用 `VelocityJointInterface` 和 Gazebo ODE 速度电机，轮式里程计由仿真关节反馈积分，`open_loop=false`。验收时对照轮式里程计与 Gazebo 实体位姿，检查车轮运动和车体位移是否一致。

## 重复运行

先按 [navigation_lab 安装与构建指南](../ros1_advanced_ws/src/navigation_lab/README.md)准备环境，再从仓库根目录执行：

```bash
source /opt/ros/noetic/setup.bash
source ros1_advanced_ws/devel/setup.bash
python3 scripts/smoke_projects.py --case arm
python3 scripts/smoke_projects.py --case motion
python3 scripts/smoke_projects.py --case navigation
python3 scripts/smoke_projects.py --case navigation --use-ekf false --goal-y 2.0
python3 scripts/smoke_projects.py --case slam
```

每条命令独立启动和关闭一组无 GUI 仿真，输出结果 JSON 和日志目录。机械臂及底盘运动阶段按仿真秒计时；脚本先确认仿真时钟已启用，再开始测量，JSON 中可检查 `ros_time_mode: simulation`。脚本使用独立 ROS/Gazebo 端口，拒绝复用已占用端口，并对测试设置墙钟超时。运行前加载对应工作区，使用同一对端口的命令依次执行。

SLAM 命令生成的地图保存在本次独立结果目录；其 `saved_yaml` 字段给出路径。按包内指南将路径传给 `navigation.launch map_file:=...` 可重做新地图导航；SLAM 地图与 Gazebo 世界的原点可能不同，初始位姿通过激光与地图对齐确定。

```bash
# 配置与客户端测试，不需要 Gazebo
cd ros1_advanced_ws
catkin run_tests navigation_lab --no-deps --no-status
catkin_test_results build/navigation_lab
```
